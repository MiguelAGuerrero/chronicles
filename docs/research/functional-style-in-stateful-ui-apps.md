# Draw the line at decisions, not purity

The research supports one practice above the rest: **put every branch that decides something into plain TypeScript functions that take time, ids and data as arguments, and leave I/O in a thin, few-branch shell around them.** That shell is a per-feature module, and the React screen beneath it only renders and forwards intents. This is the shared core of Bernhardt's functional core / imperative shell, Normand's actions-calculations-data and Seemann's impureim sandwich. React 19 and the React Compiler now effectively require it as well, since render must be pure and Effects are an escape hatch for syncing with external systems. A 100% pure app is not what the evidence supports. React itself says local mutation is "absolutely fine". Elm-style effects-as-data adds plumbing and makes behaviour harder to trace, so it earns its cost only in flows with many branches. Testing the shell against mocks or call logs couples tests to implementation, and a verified fake asserted on its final state does better. Most of this is well-argued practitioner and vendor consensus rather than measured fact. **No controlled study shows that functional core / imperative shell (FCIS) improves UI maintainability. None shows that it makes AI agents more successful either.** One study found modularity did not consistently help LLM code generation. For Chronicles, the owner's Nov 1 plan is mostly sound. The research argues for four changes: enforce the boundary in tests and lint rather than hand-kept allow-lists; assert final state by default and the call log only when order is the requirement; reserve reducers for the walk lifecycle and the recorder; and take walk.tsx apart one effect cluster at a time rather than as one big slice.

## One rule from three traditions: branches inward, dependencies outward

Gary Bernhardt introduced "functional core, imperative shell" in his 2012 SCNA talk "Boundaries" and a Destroy All Software screencast. His screencast states the benefits: testing the functional pieces "often naturally allows isolated testing with no test doubles", and the shell ends up with "few conditionals, making reasoning about the program's state over time much easier" ([DAS screencast](https://www.destroyallsoftware.com/screencasts/catalog/functional-core-imperative-shell)). Practitioner notes on the talk summarise the dividing line as "many paths, no dependencies" for the core and "few paths, many dependencies" for the shell. The same notes argue that integration tests "don't scale because of the number of paths" ([pepasibble notes](https://gist.github.com/pepasibble/4ae4223d7948c20affc487e2ca64755a)). That criterion is mechanical, which matters for agents: **an `if` that decides goes in the core, and a call that touches the world goes in the shell.** Neither source gives a size for the shell in lines.

Eric Normand's *Grokking Simplicity* supplies the refactoring move ([Manning](https://www.manning.com/books/grokking-simplicity)). Code is data, calculations or actions. A function becomes an action when information enters or leaves it implicitly: through globals, mutation, I/O or the clock. You extract a calculation by making each implicit input an argument and each implicit output a return value ([book quoted in explicitness-checker #72](https://github.com/jonbaldie/explicitness-checker/issues/72)). His **action spreading rule** explains how screens grow 35 effects. Any function that calls an action becomes an action, and so does every caller above it ([Manning liveBook](https://livebook.manning.com/learn/concepts/normand--action-spreading-rule/grokking-simplicity)). One database read inside a decision helper therefore drags the whole decision into a `useEffect`. Both Normand and Kris Jenkins reject dogmatic purity. Normand says an action with one implicit input beats one with two, even when you cannot reach zero. Jenkins's formulation is to eliminate side-effects and side-causes "wherever we can, and tightly control them whenever we can't" ([Jenkins 2015](https://blog.jenkster.com/2015/12/what-is-functional-programming/)).

The tradition has one important limit for UI code. Mark Seemann's impureim sandwich (gather impure data, call a pure function, then act on its result) fits one-shot interactions ([ploeh, Impureim sandwich](https://blog.ploeh.dk/2020/03/02/impureim-sandwich/)). By his own account it is "no longer possible" for interactive software, which is a long-lived loop of events ([ploeh, Pure interactions](https://blog.ploeh.dk/2017/07/10/pure-interactions/)). The Elm Architecture's answer is to run the sandwich once per event: `update : Msg -> Model -> (Model, Cmd Msg)` is pure, and the runtime executes the returned commands ([Pusher on Elm 0.17](https://pusher.com/blog/realtime-elm-revisited-with-elm-0-17/)). A walk screen needs this per-event framing, because a GPS fix arrives every second or two. Evidence status: the principle is **well established as practice and argument**. Its benefits are **asserted, not measured**. The foundational sources (2012–2016) predate React hooks. Most of them were read here only through search extracts, because their hosts were blocked from this session.

## React 19 and its compiler already require a functional core

React's own documentation describes a three-tier split, and that split is a functional core. Rendering code "must be pure. Like a math formula, it should only *calculate* the result". Event handlers "*do* things". Effects are "an escape hatch" for synchronising with an external system "because the component was displayed" ([react.dev, Synchronizing with Effects](https://react.dev/learn/synchronizing-with-effects); [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)). The same page is explicit about three things:

- Values computable from props or state should be calculated during render, not stored through an Effect.
- Chains of Effects that set state only to trigger each other are "rigid and fragile", and they cost a render per link.
- "The fewer raw `useEffect` calls you have in your components, the easier you will find to maintain your application."

Reducers "must be pure", and a reducer "doesn't depend on your component", so "you can export and test it separately in isolation" ([Extracting State Logic into a Reducer](https://react.dev/learn/extracting-state-logic-into-a-reducer)). For state held outside React, `useSyncExternalStore` is "less error-prone than manually syncing mutable data to React state with an Effect". Its snapshot must be immutable and cached while unchanged ([useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore)). All of this is **official guidance and well established**.

The React Compiler raises the stakes. Version 1.0 (October 2025, on by default since Expo SDK 54) memoizes automatically on the assumption that the Rules of React hold. Its validation passes now ship as lints in `eslint-plugin-react-hooks`: `purity`, `refs`, `set-state-in-effect`, `immutability` and `globals` ([React Compiler v1.0](https://react.dev/blog/2025/10/07/react-compiler-1)). When the compiler detects a violation, it **"automatically skips over those components and hooks"** ([eslint-plugin-react-hooks](https://react.dev/reference/eslint-plugin-react-hooks)). A large impure screen can therefore lose its optimisation without any visible failure. The gotchas Chronicles' AGENTS.md lists for the compiler (lazy initializers for `Date.now()`, no `ref.current` in render, setState from callbacks) are these official rules. Pure `(trace, pauses, now) => viewModel` functions called in render satisfy the compiler and `tsx --test` at once.

React is equally clear that purity is not the goal in itself. "*Local* mutation is absolutely fine … There is no need to contort your code to avoid local mutation". What matters is that components are idempotent, not that they are "100% pure in the strict functional programming sense" ([Components and Hooks must be pure](https://react.dev/reference/rules/components-and-hooks-must-be-pure)). Rich Hickey makes the same argument for Clojure's transients: "you simply can't get as fast using only pure functions and immutable data", and immutability is essential "once constructed and shared" ([clojure.org, Transients](https://clojure.org/reference/transients)). Immer's documentation warns that calling `produce` per item is "exponentially slower" than batching inside one producer ([Immer performance](https://github.com/immerjs/immer/blob/main/website/docs/performance.mdx)). For a GPS trace this is arithmetic, not a benchmark. A 3-hour walk at one fix per second is about 10,800 points. Rebuilding the array with `[...trace, fix]` on every fix copies roughly **58 million references over the walk**. The pattern that both React and Clojure endorse is to keep the buffer mutable and append-only inside the store, update aggregates incrementally, and publish an immutable snapshot through `getSnapshot` within the walk screen's existing budget (the e2e fails above **2.5 renders/s**, per `docs/ARCHITECTURE.md`).

### What this looks like on walk.tsx's fog refresh

`src/app/walk.tsx` is **1,714 lines with 35 `useEffect` calls**. Its fog effect shows the problem compactly. One effect body does six things:

1. Gates on five conditions (no position, no tile build, riding, a run already busy, moved under 100 m).
2. Reads the map's loaded tiles through `mapRef`.
3. Writes segments and places to the db.
4. Reads nearby segments back and the visited set once per screen.
5. Checks `mountedRef`.
6. Computes the fog with a one-line pure filter before calling `setFog` and `setWalked`.

It also keeps three refs (`fogRun`, `visitedRef`, `liveRuns`), one of them mirrored from props by a separate effect. Two of those steps are decisions: whether a refresh is due, and which segments count as fog. Both are calculations that Normand would extract as they stand:

```ts
// core (no React, I/O or clock): unit-tested in milliseconds
export function fogDue(s: { here: LngLat | null; build: string | null; riding: boolean;
  busy: boolean; lastAt: LngLat | null }): boolean
export function fogOf(segs: StreetSegment[], visited: ReadonlySet<string>,
  runs: LngLat[][]): { fog: StreetSegment[]; walked: StreetSegment[] }

// shell: one feature module, ports passed in; the map read is a function the view hands over
export async function refreshFog(p: Pick<Ports, 'db'>, read: () => Promise<MapView | null>,
  here: LngLat, build: string, runs: LngLat[][]): Promise<void>  // writes, reads, then store.set(fogOf(...))
```

With this split the `mountedRef` dance disappears, because the result lands in a store that outlives the screen rather than in component state. The ordering rule "write segments, then read them back" becomes something a shell test can pin down. One detail does not fit the textbook. The map reader is an imperative handle owned by a component, not a global port. The view must therefore pass it into the shell as a function. Not every external dependency can live in a `Ports` record.

## Test the shell against verified fakes, and assert outcomes

The testing literature agrees on an order of preference, and this is **well established**. *Software Engineering at Google* says to use the real implementation where feasible, then a fake, and only then stubs or interaction testing. It also calls interaction tests brittle because they check how a result was reached rather than the result itself ([SWE at Google ch. 13](https://abseil.io/resources/swe-book/html/ch13.html); [ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)). Fowler frames the same choice as state verification against behaviour verification ([Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)). Vladimir Khorikov adds a split that maps neatly onto Chronicles:

- **Managed** dependencies are ones only your app touches, such as its own database. Use them for real, or as a faithful stand-in, and assert on state. "Don't mock your database, it's an implementation detail" ([Khorikov](https://vkhorikov.medium.com/dont-mock-your-database-it-s-an-implementation-detail-8f1b527c78be)).
- **Unmanaged** dependencies have effects others can observe. OS notifications and the location recorder fall here, and that is where checking interactions is justified.

A fake is only as good as its fidelity. The established remedy is one contract suite run against both the fake and the real adapter ([Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html); [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)). Drift is common when that suite is missing. In one real PR, a **fake failed 27 of 50 contract scenarios that the real adapter passed** ([amd_middleware PR #292](https://github.com/Data-Buddies-Solutions/amd_middleware/pull/292)). A mobile-tooling repo had contracts for only **9 of 185 fakes** ([auto-mobile #11868](https://github.com/kaeawc/auto-mobile/issues/11868)). James Shore's Nullables go further and embed the fake inside the production wrapper. His Output Tracking records domain-meaningful outputs instead of the functions that were called ([Shore, Testing Without Mocks](https://www.jamesshore.com/v2/projects/nullables/testing-without-mocks)). Kent C. Dodds's Testing Trophy weights integration tests most heavily ([Dodds](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)). That supports moving orchestration coverage out of a slow e2e and into fast shell tests.

The redux-saga ecosystem is a natural experiment in what happens with exact-sequence assertions. Sagas yield plain-object effects, so a test can deep-equal every step. The library's own test-plan tooling calls such tests "tightly coupled to the saga implementation" and offers final-state testing as the less brittle alternative ([redux-saga-test-plan](https://github.com/jfairbank/redux-saga-test-plan); [Scott Logic 2018](https://blog.scottlogic.com/2018/01/16/evaluating-redux-saga-test-libraries.html)). The practical rule, which is **well-supported inference**: **assert the fake db's final state by default.** Assert the call log only when order or occurrence is the specification. Examples are the Capture row written before the file moves, the recorder stopped before saving, a double-tap producing one row, and the notification cancelled at stop. When you do assert the log, log domain events (`capture.saved`), not method names, so a refactor does not break the test.

Time, ids and randomness should be **injected as values into the core and as functions into the shell**. Seemann says to keep clock reads at the edge and pass their values inward ([What's a sandwich?](https://blog.ploeh.dk/2023/10/09/whats-a-sandwich/)). Fake timers patch globals, freeze time until advanced, do not flush promises, and leak across tests ([jest #2684](https://github.com/jestjs/jest/issues/2684); [Sinon fake timers](https://sinonjs.org/concepts/fake-timers/use-fake-timers)). A timeout is better modelled as an event (`{type: 'tick', now}`) that the shell feeds in, so the throttle decision `shouldReroute(lastAt, now)` stays pure.

## Reducers and state machines earn their plumbing only in tangled flows

Effects-as-data is the strongest form of the pattern, and also the most expensive. redux-loop ports Elm to Redux so that reducers "describe the effect" and can be tested "without worrying about waiting for effects to finish" ([redux-loop](https://github.com/redux-loop/redux-loop)). Critics name its costs. Command plumbing is "more verbose than just calling fetch()" ([bhekani on TEA](https://digitalgarden.bhekani.com/the-elm-architecture-tea/)). One user action can require "trac[ing] through multiple Cmd/Msg cycles" to see what the program does ([Interjected Future](https://interjectedfuture.com/elm-should-have-had-algebraic-effects/)). Both of these are **opinion**, but they are consistent with each other.

Statecharts have the only quantitative UI evidence in this review, and it is thin. Harel's 1987 formalism adds hierarchy and orthogonal regions to flat machines ([Harel 1987](https://dubroy.com/refs/Statecharts_a_visual_formalism_for_complex_systems.pdf)). Horrocks reported **80–90% fewer bugs** in modules designed with statecharts. That figure comes from a single author's own projects and is reported second-hand through statecharts.dev ([statecharts.dev](https://statecharts.dev/benefit-low-bug-count.html)). The same site lists real drawbacks: the paradigm is foreign to most developers, someone experienced has to lead, there is an extra library, and type safety between chart and component is hard to achieve ([drawbacks](https://statecharts.dev/drawback-foreign-paradigm.html)). XState is called overkill for simple interactions ([lonboard #916](https://github.com/developmentseed/lonboard/issues/916)). Its model-based testing tooling has moved three times, from v4 `@xstate/test` to v5 `xstate/graph` and back to `@xstate/test` in the v6 alpha ([XState PR #5627](https://github.com/statelyai/xstate/pull/5627)).

A defensible threshold is to promote a flow to an explicit machine when at least two of the following hold:

- Three or more flags combine into impossible states.
- Async work can be cancelled, superseded or retried.
- Timers drive transitions.
- The flow must resume after a reload.
- The same event means different things in different phases.

David Khourshid's critique of boolean-flag UIs makes the same case from the other side ([Stately blog](https://prod.stately.ai/blog/2019-11-13-no-disabling-a-button-is-not-app-logic)). This threshold is **inference from practitioner consensus**, not a measured cut-off. In Chronicles, the walk lifecycle (start, pause, resume, stop, permission loss, backgrounding) and the voice-memo recorder (recording, too-short, saving, undo window, retry) qualify. The fog refresh does not: it is a one-pass sandwich. The lightweight form needs no library. A discriminated-union state plus `step(state, event, now) => { state, effects }` keeps the "impossible states unrepresentable" benefit and runs under `tsx --test`. A small breadth-first walk over the reachable states can check invariants without depending on XState's tooling. What you give up is Harel's hierarchy and parallel regions. XState is worth asking the owner about only if recording-during-pause needs those.

## Mechanical checks beat prose, but the agent evidence is thin

The guidance on agents is **consistent vendor and practitioner opinion, not measurement**. Anthropic's Claude Code guidance says CLAUDE.md is advisory ("Claude is allowed to decide a guideline doesn't apply"). Anything that must happen every time belongs in a hook or check. Also: "If you ever find yourself at forty of them, most are probably preferences" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). OpenAI's harness-engineering report describes about 1M agent-written lines whose domain layering was "enforced mechanically via custom linters … and structural tests", with remediation in the error messages ([OpenAI](https://openai.com/index/harness-engineering/)). Thoughtworks distinguishes guides from sensors and advises turning whatever can be made deterministic into a sensor ([Thoughtworks podcast](https://www.thoughtworks.com/insights/podcasts/technology-podcasts/what-harness-engineering)).

The empirical work is more sobering. An ICLR 2026 study found that developer-written context files had small effects on agent task success, and its v2 calls those effects not statistically significant. LLM-generated files cut success slightly and raised cost by **more than 20%** ([Gloaguen et al.](https://arxiv.org/abs/2602.11988)). A 2026 review reports structural erosion in **77% of trajectories** where agents repeatedly extend their own code. Quality guidance reduced initial verbosity but "not the degradation rate" ([arXiv 2610.38977](https://arxiv.org/html/2610.38977v1)). That favours a ratchet the tools enforce over a rule that only asks. The one study of modularity found it "does not consistently improve performance" of LLM code generation ([survey, arXiv 2511.10271](https://arxiv.org/pdf/2511.10271)). **No study tests whether FCIS helps agents.** The case for it is an analogy: small units with explicit inputs are cheap to test, and tests are the feedback channel the vendors rank highest.

On tooling, which is **established tool behaviour**, only graph tools check transitive reachability: dependency-cruiser's `reachable` rules ([rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)) and Nx tags ([Nx](https://nx.dev/docs/features/enforce-module-boundaries.md)). ESLint import rules see one file at a time. Even so, a direct rule of the form "a core file imports only core files, pure packages, or types" implies transitive purity by induction. No mainstream tool reads a per-file header tag, so a tag needs a small custom check. Three mature ratchets replace hand-kept lists:

- **ESLint bulk suppressions** (v9.24+) record violations per file *per rule as counts*. `--prune-suppressions` removes entries that no longer occur ([ESLint suppressions](https://eslint.org/docs/latest/use/suppressions)).
- **dependency-cruiser's `--baseline-mode shrink-only`** never admits new violations ([depcruise CLI](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md)).
- **Betterer** fails when results get worse and tightens its snapshot when they improve ([Betterer](https://phenomnomnominal.github.io/betterer/docs/eslint)).

For impurity inside a core file, core ESLint's `no-restricted-properties` and `no-restricted-syntax` can ban `Date.now`, `Math.random`, bare `new Date()` and top-level `let`, each with a fix-it message. eslint-plugin-functional's own strict preset is meant to "strictly enforce functional programming" and ships lenient presets because the strict one fights ordinary code ([eslint-plugin-functional](https://npmjs.com/package/eslint-plugin-functional)). That argues for a handful of targeted rules over the plugin.

## Where these patterns break down

Each pattern has a documented failure mode:

- **FCIS does not reach lifecycle bugs.** Unmount races, permission prompts, backgrounding and native module behaviour live in the shell, and they are the bugs a shell test against fakes cannot see. In Chronicles **native code has never run on a device**, so no layering makes the native adapters verified.
- **The contract suite covers web only.** It can check the fake against IndexedDB through `fake-indexeddb`, which is itself a polyfill. The SQLite adapter cannot run under `tsx --test` at all.
- **Effects-as-data costs traceability.** It is the wrong default for single read-and-display flows.
- **Ports add ceremony.** Hexagonal architecture is criticised for vocabulary and layering overhead ([Merchan](https://medium.com/@oswaldo.merchan/hexagonal-architecture-what-nobody-is-telling-you-2e694eac3e6b)). Cockburn reportedly treats the number of ports as a matter of intuition.
- **Port injection has a gap.** React context can be a container, but it degrades into a service locator ([chanhle.dev](https://chanhle.dev/en/blog/hexagonal-architecture-ports-adapters)). The background location task, registered in `index.js` before React exists, needs a module-level composition root whatever the rule says.
- **Heavy FP libraries don't pay.** The criticism of fp-ts and Effect-TS centres on readability, debuggability, review cost and API churn ([HN Effect thread](https://news.ycombinator.com/item?id=40682149); [jtorchia](https://dev.to/jtorchia/functional-programming-with-typescript-what-fp-ts-teaches-you-even-if-you-never-ship-it-4a5)). The benefit here comes from where code lives, not from `pipe`.
- **Blanket immutability is too slow on hot paths.** On a growing trace it is quadratic, so the boundary must allow local mutation.

### Practices, graded by evidence

| Practice | Grade | Basis |
|---|---|---|
| Decisions in pure functions; time, ids and data passed in | Established practice; benefit argued, not measured | Bernhardt, Normand, Seemann, React docs |
| Derive in render; Effects only for external sync; few raw Effects | Established (official) | react.dev |
| Many-setState logic consolidated in a pure reducer, one event per interaction | Established (official) | react.dev, Redux style guide |
| External state via `useSyncExternalStore` with immutable snapshots and narrow selectors | Established (official) | react.dev, React-Redux, Zustand docs |
| Local mutation inside a boundary; immutable only once shared | Established (official) | react.dev, Clojure, Immer |
| Prefer fakes over mocks; assert state over interactions | Established | SWE at Google, Fowler, Khorikov |
| Verified fake via one contract suite over fake and real | Established | Fowler; drift evidence (27/50) |
| Injected clock over fake timers for domain time | Practitioner consensus | Seemann, Jest and Sinon issues |
| Call-log assertions only when order is the spec; log domain events | Inference from the above | Shore, saga experience |
| Effects-as-data and explicit machines only past a complexity threshold | Practitioner consensus; threshold is opinion | redux-loop critics, statecharts.dev, XState issues |
| Mechanical enforcement with fix-it messages; small rule set | Vendor opinion, consistent | Anthropic, OpenAI, Thoughtworks |
| Ratchets the tools enforce rather than lists people keep | Tool-established; agent benefit inferred | ESLint, depcruise, Betterer; erosion study |
| FCIS makes agents more successful | Unsupported speculation | No study found |

## Evaluating the Nov 1 plan and the Nov 3 choices

Some repository facts bear on this. The Nov 1 work sits on `origin/claude/functional-core-foundations`. Since the branches diverged, that branch has **59 commits not on main** and main has **67 not on the branch**. Its substance is one additive commit, `561b439`: 16 files and 1,136 lines covering ports, fakes, the Db contract, typed meta, the store and the lint lists. A second commit adds **84 lines to AGENTS.md**. The lockfile pins **ESLint 9.39.5**, so bulk suppressions are available. `docs/ARCHITECTURE.md` already defines "pure" transitively ("directly or through what it imports; type-only imports don't count") and marks **65 entries** `(pure)`. Nothing checks those marks.

| Element | What the research says | Suggested change |
|---|---|---|
| Three layers: core, shell, view | Strongly supported (FCIS plus React's render/handler/Effect tiers) | Keep. Add "adapter" as a fourth tag for the db, recorder and notifier implementations, which are neither core nor feature shell |
| `Ports` object as parameter | Supported (Cockburn); low ceremony at this size | Keep. Have each shell take `Pick<Ports, …>`. Allow view-owned handles (the map reader) as plain function arguments. Name `index.js` as the second composition root |
| Shell as only writer; Store via `useSyncExternalStore` | Supported (react.dev for non-React state) | Keep. Require cached immutable snapshots and primitive or narrow selectors, so the 2.5 renders/s budget holds |
| Shell tests first, against fakes with a shared call log and `failNext` | Fakes supported; call-log default contradicts SWE at Google and Khorikov | Assert final fake-db state by default. Use the log only for order the spec states, for unmanaged ports (notifier, recorder) and for re-entry. Log domain events. Label `failNext` modes that the real adapter cannot reproduce as fake-only |
| Db contract suite over fake and IndexedDB | Strongly supported; drift is common without it | Keep, and make it the first thing that ships. Record the SQLite adapter in `NATIVE_UNVERIFIED.md` |
| Effects-as-data reducers only for many-branch machines | Supported | Keep. Write the two-of-five threshold into the rule. Name the walk lifecycle and recorder as candidates, and the fog refresh as a sandwich |
| Typed meta keys | Not covered by the research | Keep as a cheap type-level guard. No evidence either way |
| No module-level mutable state in new code | Supported (global fake-timer leakage, implicit inputs) | Phrase it as "outside the composition roots". Enforce top-level `let` with `no-restricted-syntax` on core and shell files |
| `LEGACY_*` allow-lists that only shrink | Superseded. Nothing enforces "only shrink", and a file-level entry lets a listed file gain unlimited new violations | Replace with ESLint bulk suppressions (counts per file and rule) and, for the tag check, a JSON baseline that fails on both new and stale entries |
| Nov 3: header tag plus a check in `npm test` | Viable. No tool reads tags, so it is custom. It keeps files in place, which suits Expo Router and the `.native.ts`/`.web.ts` splits | Keep the tag as the single declaration. Have the test enforce the direct rule and print the import path on failure. Derive ESLint's core file list from the tags, so ambient-effect bans show at the line (this hybrid is untested speculation; fall back to a `.core.ts` suffix if it proves flaky). Retire the `(pure)` prose marks so there is one source of truth |
| Nov 3: convention, then walk.tsx as the first slice | Strangler fig and Feathers-style sprouting are supported; a single-slice rewrite of a 1,714-line screen covered only by a web e2e is not | Make walk.tsx the first *target*, taken one effect cluster per slice, each behind the e2e as a characterization test |

The recommended order follows from the evidence:

1. **Write the convention** as `.claude/rules/functional-core.md` plus a decision record, not 84 more lines in AGENTS.md. Anthropic's guidance and the ICLR study both favour short context files that point elsewhere.
2. **Cherry-pick `561b439`** onto main rather than merging the diverged branch. Drop its `LEGACY_*` lists and re-run its contract suite.
3. **Tag the existing pure modules mechanically, and add the `npm test` check with a generated baseline**, so that slices from now on stop adding debt. Every slice since Nov 1 has added to it.
4. **Add the small core-only lint set** (`Date.now`, `Math.random`, bare `new Date()`, timers, top-level `let`), with bulk suppressions for what already exists.
5. **Start walk.tsx with the fog refresh.** Extract `fogDue` and `fogOf` test-first, then `refreshFog` against the fake db with an ordering test, then point the screen at the store. Move to the lifecycle reducer only once the threshold is confirmed.
6. **Treat the pilot as the experiment that the literature lacks.** Track walk.tsx's effect count, shell-test time against e2e time, and regressions from agent-made changes in refactored and untouched areas.

## Conclusion

The research shifts the question from "how functional should Chronicles be" to "where does each decision live, and what fails when one is in the wrong place". React already answers most of the first half officially. The project's gap is enforcement, not doctrine. Chronicles has done the hard part: about 100 pure modules with a 6-second suite. What it lacks is a check that would stop the 101st from quietly importing the db, and a seam that would let the walk screen's orchestration be tested without a browser.

The weakest link is the claim that motivates the work most directly: that this structure makes agents better maintainers. Nothing measured supports it yet. What is measured, that agent code erodes and that guidance slows erosion without stopping it, argues for enforcement ratchets more than for any particular architecture. The walk.tsx pilot is therefore worth running carefully and measuring. Done that way, it would produce the first real evidence for or against the owner's bet.
