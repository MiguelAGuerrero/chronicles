# Five platform limits reshape the walking chronicle

The design mostly holds up, but five platform facts change how it gets built. First, **MapLibre offline packs cannot download a `pmtiles://` source**, so downloadable regions have to be PMTiles extracts the app manages itself. Second, **stock expo-location cannot silently resume a session after the app is terminated**: it uses classic `startUpdatingLocation` and never creates a `CLBackgroundActivitySession`, so silent resume needs a small native module built on iOS 17's `liveUpdates` API. Third, **iOS geofences are useless at 50–75 m**: there is a 20-region cap, a ~200 m test cushion, a 20 s dwell, and enter/exit events typically arrive 3–5 minutes late. Reveal and recall checks must therefore run as distance tests inside the live location task, followed by an immediate local notification. Fourth, **"no server of its own" still means renting a bucket**. Protomaps' hosted API does not serve raw PMTiles, and its download mirror is not meant to be hotlinked, so the planet (about 120 GB) has to live in R2 (about $1.80/month), with versioned filenames to avoid a MapLibre cache-corruption bug. Fifth, **phone GPS cannot tell which side of the street you walked**: GNSS picked the correct sidewalk 47% of the time downtown. In North America, sidewalks mapped as separate OSM ways must be merged into the street they belong to, or fog will never clear cleanly. The surrounding evidence points the same way. A CityStrides-style 25 m buffer with coverage thresholds beats a full HMM matcher for v1. A fixed ~40 s replay driven by `line-gradient` beats Strava Flyover's "60 seconds per hour" pacing. Discovery's 2–3 alerts per session is already stricter than any shipped location game. The remaining risks are gaps nobody has measured: how fast MVT decoding and matching run under Hermes on a phone, whether `liveUpdates` relaunches after a swipe-kill on iOS 26+, and what a free-Apple-ID sideloaded build can carry in entitlements.

## The five findings that change the plan

The table summarizes the design changes. Each one is developed in its subsystem section below.

| Original assumption | What the evidence says | Required change |
|---|---|---|
| Regions downloadable via MapLibre offline packs over the hosted planet | `createPack` cannot fetch `pmtiles://` tiles; feature request #2352 is open with no timeline | Download per-region `.pmtiles` extracts (or individual tiles) to `Paths.document`, and add them as a second source |
| expo-location resumes the session if the app is killed | Classic `startUpdatingLocation` never relaunches a terminated app; expo-location adds no `CLBackgroundActivitySession` | Write a native module using `CLLocationUpdate.liveUpdates` + `CLBackgroundActivitySession`, recreated in the AppDelegate at launch; plan for Always authorization |
| Geofences or `UNLocationNotificationTrigger` can fire 50–75 m reveals | 20-region cap, ~200 m cushion, 20 s dwell, 3–5 min average latency, under 100 m unreliable | Check distances in the background location task and fire `trigger: null` local notifications |
| Hosted planet PMTiles needs no infrastructure | Protomaps API serves ZXY only; build downloads must not be hotlinked; MapLibre caches stale byte ranges after a rebuild | Copy the planet to an R2 bucket you own, use versioned filenames, and refresh weekly to monthly |
| Street segments can be credited one OSM way at a time | In separate-sidewalk regions one street becomes three parallel ways; GNSS sidewalk choice is a coin flip | Credit "street units" (centerline plus its sidewalk ways); crossings count toward the street they cross |

The first two changes add native code to an otherwise JavaScript app. A solo developer without a Mac can still do this, because Expo config plugins and local modules compile in the GitHub Actions build. The notes, however, contain no evidence on whether a free-Apple-ID sideloaded build keeps the `location` background mode, Always authorization behavior, or the Time Sensitive notification capability intact. That has to be tested on a device first, before anything else is built on top of it.

## Recording: backgrounding is easy, surviving termination needs native code

### How comparable apps do it

Shipping GPS track recorders converge on one Core Location recipe. They set `allowsBackgroundLocationUpdates = true` with `location` in `UIBackgroundModes`, start updates from the foreground, use `activityType = .fitness`, turn `pausesLocationUpdatesAutomatically` off, use best accuracy, set no distance filter or one of about 3 m, and turn the background indicator on. One long-running track recorder adds a `CLBackgroundActivitySession` on iOS 17+ ([Apple Forums 773639](https://developer.apple.com/forums/thread/773639); [Apple Forums 765927](https://developer.apple.com/forums/thread/765927)). Since iOS 16.4, an app that pairs `startUpdatingLocation` with significant-change monitoring **can be suspended if it asks for low accuracy or a distance filter**. Apple's escape hatches are `kCLDistanceFilterNone` with accuracy of 100 m or better, or turning on the background indicator ([Apple Forums 726945](https://developer.apple.com/forums/thread/726945?page=2)). This matters directly because **expo-location 19.0.8 calls exactly that pair back to back and never creates a `CLBackgroundActivitySession`**. An Expo developer traced 2–9 minute gaps to two causes: the indicator lapsing about 60 s after backgrounding, and a map with about 750 children re-rendering in the background at about 150 ms per delivery. Adding the session natively and pausing UI work brought delivery cost under 20 ms, and a 22-minute drive then recorded with no gaps ([Apple Forums 844579](https://developer.apple.com/forums/thread/844579)). Apple DTS separately warns that a callback that cannot keep up with once-per-second updates eventually stops receiving them ([Apple Forums 786558](https://developer.apple.com/forums/thread/786558)).

Termination is the harder problem. DTS is explicit: "Most APIs will cause a relaunch. startUpdatingLocation() will not" ([Apple Forums 786487](https://developer.apple.com/forums/thread/786487)). To continue GPS-level updates after a kill, an app "will need to use the new CLLocationUpdate's liveUpdates(_:)" ([Apple Forums 763166](https://developer.apple.com/forums/thread/763166)). WWDC23 describes the contract. The system relaunches the app in the background, and the app must "restart the updates by calling liveUpdates" and "recreate a CLBackgroundActivitySession" immediately at launch, before anything else ([WWDC23 10180](https://nonstrict.eu/wwdcindex/wwdc2023/10180/)). Apple's sample code persists `updatesStarted` and `backgroundActivity` flags and restores both in `didFinishLaunchingWithOptions` ([Apple sample](https://developer.apple.com/documentation/corelocation/supporting-live-updates-in-swiftui-and-mac-catalyst-apps.md)). **A new session can only be created in the foreground.** If the app invalidates the session and then tries to recreate it after a background relaunch, it gets no background location rights at all ([Apple Forums 767460](https://developer.apple.com/forums/thread/767460)). DTS also warns against stopping live updates while the device is stationary: if the app is terminated in that state, it is never relaunched ([Apple Forums 810433](https://developer.apple.com/forums/thread/810433)).

Swipe-kill is where the evidence conflicts. One developer reports that `liveUpdates` does not resume after an App Switcher swipe ([Apple Forums 774955](https://developer.apple.com/forums/thread/774955)). Another reports that significant-change and region monitoring stopped relaunching after force-quit on iOS 26.4.2, although the same code worked on iOS 18 ([Apple Forums 826964](https://developer.apple.com/forums/thread/826964)). Neither thread has an Apple answer. The incumbents treat interruption as normal. AllTrails shows "your activity was paused because the app closed" with a Resume button ([AllTrails help](https://support.alltrails.com/hc/en-gb/articles/360018931792-Why-do-I-need-to-relaunch-the-app-when-my-iPhone-locks)). Strava tells users it "has recovered from a problem and has resumed your recording" and leaves a straight-line gap ([Strava Community](https://communityhub.strava.com/devices-and-connections-6/not-recording-completely-5475)). A third-party Expo package exists precisely because expo-location loses tracking on force-quit. It relaunches through significant-change monitoring and writes every fix to a native SQLite buffer before it reaches JavaScript ([expo-persistent-background-location](https://cdn.jsdelivr.net/npm/expo-persistent-background-location@0.1.3/README.md)).

Fix filtering in production is simple gating, not clever math. Apple's sample drops fixes with negative accuracy and fixes older than 5 s ([Apple LocateMe](https://developer.apple.com/library/archive/samplecode/LocateMe/Listings/LocateMe_TrackLocationViewController_m.html)). Map My Tracks accepts only fixes with 50 m accuracy or better and caps speed at 300 km/h ([Map My Tracks](https://maps.mapmytracks.com/blog/entry/how-map-my-tracks-delivers-pinpoint-gps-accuracy-for-your-activities)). Avenza defaults to 32 m, with 8/16/32 m presets ([Avenza](https://support.avenzamaps.com/hc/en-us/articles/4961280327956-GPS-Settings)). Strava tells walkers to turn auto-pause off and computes moving time after upload instead ([Strava auto-pause](https://support.strava.com/hc/en-us/articles/216929827-How-to-Fix-Autopause-Issues)). The only published battery figure is AllTrails' "typically 10-15% … per hour" ([AllTrails](https://support.alltrails.com/hc/en-us/articles/360019244951-Saving-battery-while-using-Navigate-to-record-an-activity)).

### Recommended parameters

For the session itself, use best accuracy, no distance filter, `.fitness`, auto-pause off, and the indicator on. Start from a foreground tap only. Keep the background task to "append raw fix to SQLite, run cheap proximity checks, return," with no map or React work while backgrounded. Store every fix raw: lat/lon, altitude, horizontal and vertical accuracy, speed and speed accuracy, course and course accuracy, and timestamp. Compute acceptance at read time. Reject negative accuracy and fixes older than 5–10 s, use a working accuracy cut of 20–30 m, and drop anything worse than 50 m. Flag the cold-start fixes after a gap rather than deleting them, because one post-gap fix had 170–1,950 m accuracy and was 264 s old ([Apple Forums 844579](https://developer.apple.com/forums/thread/844579)). Auto-pause and moving time should be derived views over the raw trace, using a dwell of at least 2–5 minutes, which matches Transistor's 5-minute `stopTimeout` ([Transistor Config](https://app.unpkg.com/@transistorsoft/capacitor-background-geolocation@7.0.4/files/dist/declarations/interfaces/Config.d.ts)).

### What changes in the design

**Silent resume requires a native recorder and probably Always authorization.** The recommended shape is a local Expo module that does five things: starts `CLLocationUpdate.liveUpdates(.fitness)` plus a `CLBackgroundActivitySession` on "tap start"; persists an active-session flag natively; recreates both from an Expo AppDelegate subscriber before JavaScript loads; buffers fixes natively; and lets JavaScript drain them. The alternative is `expo-location/next`, a beta in SDK 58 that maps profiles onto `LiveConfiguration`, says the system relaunches the app to deliver positions, and offers `hasStarted()` for launch reconciliation. It **requires Always on iOS**, and "Keep Only While Using" resolves as denied ([Expo location-next](https://docs.expo.dev/versions/v58.0.0/sdk/location-next.md)). When In Use plus the indicator is enough to keep recording through backgrounding ([Apple: authorization choice](https://developer.apple.com/documentation/bundleresources/choosing-the-location-services-authorization-to-request.md)). Apple has not confirmed whether it is enough for relaunch after termination. Ask for When In Use at the first walk and upgrade to Always only with a clear explanation. On iOS 13.4+ the upgrade prompt appears immediately, and an app gets only one Always request ([Apple Forums 674398](https://developer.apple.com/forums/thread/674398)).

One more design change follows from the raw-trace principle. **`.fitness` can snap fixes onto known paths before the app ever sees them.** In one case the reported track kept going straight for about 200 m past a turn, while showing good reported accuracy ([Apple Forums 765927](https://developer.apple.com/forums/thread/765927)). The "raw" trace is therefore partly Apple-corrected. Store `activityType` with each session and keep `.other` as a field-testable flag. Every resume should start a new segment in the trace, and the replay should show that segment boundary rather than interpolate across it. For a pocket-first stop control, ActivityKit allows App Intent buttons, but a Live Activity "can't … receive location updates." Strava's Live Activity has no pause or stop at all ([Apple ActivityKit](https://developer.apple.com/tutorials/data/documentation/activitykit/displaying-live-data-with-live-activities.md); [Strava Live Activities](https://support.strava.com/en-us/articles/15401559-strava-live-activities-on-ios)). Treat the Live Activity as a status display, not a mechanism for keeping the app alive.

## Street model and matching: a 25 m buffer beats an HMM on tile-derived streets

### How comparable apps do it

The two largest street-completion products use geometry rules, not probabilistic matchers. **CityStrides buffers the activity's path line by 25 m.** It marks every OSM way node inside the buffer, completes a street at 90% of its nodes (100% for streets with fewer than about 10 nodes), and has used that radius "since I started in 2013" ([CityStrides data explainer](https://community.citystrides.com/t/about-the-node-street-and-city-data/19802); [Node detection thread](https://community.citystrides.com/t/node-detection-algorithm-changed/29633)). Release 536 in March 2022 switched from individual GPS points to the path line, so straight-line gaps now credit nodes along the interpolated line. That turned tunnels and pause-and-move gaps into "flyover" lines ([Street progressed thread](https://community.citystrides.com/t/street-progressed-instead-of-completed/26449); [Long lines thread](https://community.citystrides.com/t/long-lines-not-linked-to-activity/29716)). Its best-known flaw is phantom completion. Many straight streets have nodes only at intersections, so walking past both ends completes them, and in July 2025 the developer called this "a shortcoming of CityStrides." In October 2025 he was considering densifying to a node every ~25 m ([Mid-block nodes thread](https://community.citystrides.com/t/nodes-at-intersections-but-not-mid-block/21885); [Add more nodes](https://community.citystrides.com/t/add-more-nodes-per-street/27654)). **Wandrer stores "an OSM way ID and ranges for the completed portions"** and derives walked geometry with `ST_LineSubstring` ([Wandrer engineering post](https://news.wandrer.earth/2026/01/30/wandrer-untraveled-roads.html)). It publishes no tolerance, and it concedes that points sometimes match a parallel road ([Wandrer FAQ](https://wandrer.earth/faq)). Fog of World skips streets entirely. It uses a Web-Mercator bitmap 2^22 cells wide, about 9.55 m per cell at the equator, which "lines up 1:1 with map pixels at zoom 14" ([defog README](https://github.com/leonardoazeredo/defog); [parser](https://github.com/CaviarChen/Fog-of-World-Data-Parser/blob/main/parser.py)).

Routing engines all implement the Newson & Krumm HMM. It uses Gaussian emission with σ_z = 4.07 m, an exponential transition on |great-circle − route distance|, 200 m candidates, and Viterbi decoding ([Newson & Krumm 2009](https://microsoft.com/en-us/research/wp-content/uploads/2016/12/map-matching-ACM-GIS-camera-ready.pdf)). Valhalla's Meili defaults to σ 4.07 / β 3, with a published pedestrian override of `search_radius` 25 m and `turn_penalty_factor` 100. Its docs suggest trying 500 for jittery pedestrian traces ([valhalla.json](https://gist.github.com/buma/7b52c234c559879e0c6bfd9aa222ef6d); [Valhalla docs](https://valhalla.github.io/valhalla/api/map-matching/)). Mapbox recommends `radiuses` of 20–50 m for noisy traces, with a 50 m maximum ([Mapbox v5](https://docs.mapbox.com/api/navigation/map-matching.md)). The catch is structural. OSRM's maintainer says the engine needs ways connected at intersections plus OSM-style tags, otherwise the network is "basically junk" ([osrm-backend #5960](https://github.com/Project-OSRM/osrm-backend/issues/5960)). Vector tiles carry neither shared-node topology nor unclipped geometry. No maintained JavaScript HMM or WebAssembly build of OSRM or Valhalla was found.

The pedestrian error budget is larger than engine defaults assume. **An in-hand iPhone 13 in downtown San Francisco had a median error of 13.6 m and a 90th percentile of 48.2 m, and picked the correct sidewalk 47% of the time** ([Dubiner et al. 2026](https://arxiv.org/pdf/2601.22406)). A dedicated logger walking in Copenhagen had a median error of 3.9 m ([Schipperijn et al. 2014](https://public-pages-files-2025.frontiersin.org/journals/public-health/articles/10.3389/fpubh.2014.00021/text)). Apple's `horizontalAccuracy` is roughly a 63–68% radius. Multiplying it by 1.73 gives about 95% containment ([Apple Forums 699996](https://developer.apple.com/forums/thread/699996)). OSM maps sidewalks two ways: as tags on the centerline (dominant in Western Europe) or as separate `footway=sidewalk` ways (dominant in North America and, since 2025, worldwide by length) ([OSM wiki: Sidewalk](https://wiki.openstreetmap.org/wiki/Sidewalk)).

### Recommended parameters

Use a buffer/nearest-segment matcher with a flatbush index. Flatbush builds an index of 1M boxes in 263 ms on desktop Node ([flatbush](https://www.npmjs.com/package/flatbush)), so 50k segments and 20k fixes is a sub-second to few-second job even with a mobile slowdown. Project coordinates once to local meters. Credit a fix to a segment when distance ≤ max(20 m, 1.7 × horizontalAccuracy), and ignore fixes worse than 50 m. Interpolate between consecutive accepted fixes, which is CityStrides' line-buffer lesson, but **refuse to interpolate across gaps longer than 60 s or implying more than ~3 m/s**. OSRM splits traces at 60 s gaps ([OSRM API](https://project-osrm.org/docs/v26.6.1/http)), and tile-hunting tools cap joins at 150 m to 1 km ([defog PR #293](https://github.com/leonardoazeredo/defog/pull/293); [Salamenderats](https://github.com/Vincent-ZxR/Salamenderats)). Credit by length, not nodes. Store covered sub-intervals per segment, Wandrer-style. Count a segment as walked when coverage is at least about 50–70%; the Heidelberg tool uses 70% of cross-profiles ([GIScience Heidelberg](https://giscienceblog.uni-heidelberg.de/?p=3758)). Segments shorter than about 2× the tolerance count once their interior is touched. Discount the first and last ~20 m of each segment next to a junction, so walking past a side street does not clear its mouth. Wandrer users complained about exactly that "start of loads of little side-streets" effect ([CityStrides forum](https://community.citystrides.com/t/have-a-city-pedal-bike-site/14336?page=2)).

### What changes in the design

**Credit the street unit, not the individual way.** In regions with separate sidewalks, merge `footway=sidewalk` and `footway=crossing` ways into their parallel carriageway using `street:name`/`is_sidepath:of:name` or proximity plus bearing. Fog then clears for the street whichever side was walked, which fits the "no side-of-street model" decision ([OSM wiki: footway=sidewalk](https://wiki.openstreetmap.org/Tag:footway=sidewalk)). Treat plazas and parks as areas where any fix counts, not as line segments ([Behr et al. 2021](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.GIScience.2021.II.12)). The private-road exclusion should copy CityStrides' tag set: `access=private|no`, `access=permit` since 2025, and `foot=no` ([CityStrides query](https://community.citystrides.com/t/osm-editing-guidelines/18541/2); [access=permit](https://community.citystrides.com/t/access-permit/27568)). Decide explicitly whether `foot=yes|designated` overrides `access=private`. StreetFerret reportedly says yes and CityStrides no ([access precedence thread](https://community.citystrides.com/t/osm-access-defaults-and-overrides/29488)). The plan's "derived on the phone, recomputed from raw traces" approach is the right defense against the most damaging CityStrides complaint: completions lost or flip-flopping after data updates, caused by buggy incremental update logic ([City progress thread](https://community.citystrides.com/t/city-progress-incorrect-completed-street-count-decreasing/25972?page=4)). Recompute affected segments deterministically, stamp each result with the tile build it used, and show a diff ("3 new streets, 1 removed"). Keep the HMM as a later recompute that runs over the stored traces.

## Tiles and offline data: region packs must be app-built PMTiles extracts

### How comparable apps do it

MapLibre Native's offline downloader fetches tiles through the HTTP file source, using a `{z}/{x}/{y}` template from TileJSON. A PMTiles source exposes only `pmtiles://<url>`, so **`createPack` never completes for PMTiles** ([maplibre-native #3691](https://github.com/maplibre/maplibre-native/issues/3691); [offline_download.cpp](https://raw.githubusercontent.com/maplibre/maplibre-native/main/platform/default/src/mln/storage/offline_download.cpp)). MapLibre's Android docs say it plainly: "PMTiles sources don't support offline pack downloads or caching" ([MapLibre Android PMTiles](https://maplibre.org/maplibre-native/android/examples/data/PMTiles/)). The caching half of that sentence is now out of date. **iOS 6.27.0 added an ambient cache for PMTiles byte ranges** (PR #4290), keyed as `url + "_mlnRange=from-to"` ([iOS CHANGELOG](https://raw.githubusercontent.com/maplibre/maplibre-native/main/platform/ios/CHANGELOG.md); [offline_database.cpp](https://raw.githubusercontent.com/maplibre/maplibre-native/main/platform/default/src/mln/storage/offline_database.cpp)). maplibre-react-native 11.5.0 bundles iOS 6.31.0, so areas the user has viewed do render offline, Google-Maps-style. Three defects come with it. The cache does not validate ETags, so **after the archive at a URL is rebuilt, old directory bytes mix with new tile bytes and every tile fails to decode** until the cache is cleared ([maplibre-native #4564](https://github.com/maplibre/maplibre-native/issues/4564)). `PMTilesFileSource` never erases in-flight requests, leaking tens of MB over two hours, and Soundscape bypassed it with its own resource provider ([Soundscape PR #1182](https://github.com/Scottish-Tech-Army/Soundscape-Android/pull/1182)). And `pmtiles://https://` URLs failed to parse on iOS 17.x in maplibre-react-native 10 ([maplibre-react-native #618](https://github.com/maplibre/maplibre-react-native/issues/618)). The ambient cache defaults to **50 MB with LRU eviction**, must be resized at startup before a style loads, and lives in `Library/Caches`, which iOS may purge ([OfflineManager Android](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.offline/-offline-manager/set-maximum-ambient-cache-size.html); [flutter-maplibre-gl](https://maplibre.org/flutter-maplibre-gl/advanced/offline-regions/)).

The closest production analogue to this design is Soundscape. It builds planet PMTiles with Planetiler, serves `pmtiles extract` regions from R2 for "less than around $5 per month," carries a schema version in each extract's metadata, and decodes MVT on the device into its own road and POI structures over a 2×2 tile grid. It joins ways across tile edges within 1 m ([Soundscape offline maps](https://raw.githubusercontent.com/Scottish-Tech-Army/Soundscape-Android/main/docs/developers/offline-maps.md); [Soundscape GeoEngine](https://raw.githubusercontent.com/Scottish-Tech-Army/Soundscape-Android/main/docs/developers/geoengine.md)). Organic Maps and OsmAnd ship prebuilt per-region binaries. Google and Apple set the UX bar. Google auto-updates offline areas over Wi-Fi when they are within 15 days of expiry ([Google Maps Help](https://support.google.com/maps/answer/7358957?hl=en)). Apple shows the size before download, auto-updates by default, and can auto-delete unused maps ([Apple HT213829](https://support.apple.com/en-us/HT213829)).

On the JavaScript side, the `pmtiles` npm package (4.5.0, one dependency, `fflate`) reads an archive through a two-method `Source` interface. Its `FetchSource` sends `Range` headers, validates ETags on every response, and raises an error if the host ignores byte serving ([pmtiles](https://www.npmjs.com/package/pmtiles)). A local-extract `Source` is a few lines over `expo-file-system`'s `FileHandle` (`offset` plus `readBytes`). Await each read, because operations on one handle are not ordered ([expo-file-system](https://docs.expo.dev/versions/latest/sdk/filesystem/)). `@mapbox/vector-tile` 3.0.0 decodes tiles and converts them to lon/lat. Protomaps road features carry a deterministic id, `(type << 44) | osm_id`, which fits safely in a JavaScript number. **Roads carry `access` from z15**, but **POIs carry no feature id** because the `setId` call is commented out ([Roads.java](https://raw.githubusercontent.com/protomaps/basemaps/main/tiles/src/main/java/com/protomaps/basemap/layers/Roads.java); [Pois.java](https://raw.githubusercontent.com/protomaps/basemaps/main/tiles/src/main/java/com/protomaps/basemap/layers/Pois.java)). Roads are merged when their attributes are identical and clipped with a 4 px buffer, so one OSM way appears as pieces in adjacent tiles, and occasionally two ways share one id. Quantization does not matter: a z15 tile unit is about 0.30 m.

### Recommended parameters

Host the planet yourself. The Protomaps API "does not serve PMTiles directly," and build downloads are explicitly not for hotlinking ([Protomaps API](https://protomaps.com/api); [Protomaps downloads](https://docs.protomaps.com/basemaps/downloads)). R2 storage for about 120 GB costs about $1.80/month with no egress fees ([Protomaps FAQ](https://protomaps.com/faq); [cost calculator](https://docs.protomaps.com/deploy/cost)). Upload with rclone, because the web UI caps uploads at 300 MB ([Cloudflare deploy](https://docs.protomaps.com/deploy/cloudflare)). Use versioned filenames (`planet-YYYYMMDD.pmtiles`) refreshed weekly to monthly. That bounds the cost of re-uploading 120 GB and sidesteps bug #4564. Raise the ambient cache to a few hundred MB at startup. Decode z15 tiles for street derivation and never decode lower zooms. Budget roughly 50–150 z15 tiles for a two-hour walk at about 100 KB each, or 5–15 MB ([PMTiles #588](https://github.com/protomaps/PMTiles/discussions/588)). The one decode budget found is 20 ms per dense tile in Node ([onyourleft #1544](https://github.com/openzigs/onyourleft/issues/1544)), so decode tile by tile as each one arrives rather than in a batch. Store segments in SQLite keyed by z15 tile and grid cell in an ordinary B-tree. A `tile_z15` ingest table records the build each tile came from, because it is not documented whether expo-sqlite compiles in R*Tree ([expo-sqlite](https://docs.expo.dev/versions/latest/sdk/sqlite/)).

### What changes in the design

Downloadable regions become **app-managed PMTiles files in persistent storage**, not MapLibre packs. There are two ways to make them. The first is per-region extracts that a GitHub Actions job prebuilds with `pmtiles extract` and uploads to the same bucket. This works best as overlapping city or county polygons with a schema version, which is Soundscape's pattern, and fits the "build in CI" constraint. The second is "download this area": the app fetches the few hundred tiles of a walk-sized rectangle one by one. The Protomaps author considers per-tile download "sufficient" for an area of only a few hundred tiles, and there is no JavaScript polygon extractor ([PMTiles #588](https://github.com/protomaps/PMTiles/discussions/588)). MapLibre reads one file per `pmtiles://` source ([discussion #3764](https://github.com/maplibre/maplibre-native/discussions/3764)), so the style needs the online planet source plus one local source per installed region, or the app has to limit how many regions can be active. Store regions under `Paths.document`, which iOS does not purge, never under `Paths.cache`. Because POIs lack ids, discovery targets need a derived key such as kind + name + rounded coordinate, deduplicated across the 8 px POI buffer. `querySourceFeatures` only covers tiles loaded for the current camera ([VectorSource docs](https://maplibre.org/maplibre-react-native/docs/components/sources/vector-source)). It works as a free seed for the visible area, but walk-ahead derivation still needs the JavaScript reader.

## Replay and media: a fixed 40-second timeline beats Flyover's 60 seconds per hour

### How comparable apps do it

Relive renders 3D fly-throughs on its servers ("can take up to 2 minutes"). It shows each photo for 2 s by default, and it **groups nearby photos into one moment because early versions "made the video stop every few seconds"** ([Relive customise](https://support.relive.com/kb/guide/en/how-to-customise-your-relive-video-6v3Xk61Aar/Steps/34446); [Relive photo location](https://support.relive.com/kb/guide/en/why-your-photos-are-in-a-different-location-OIVVTAvmqP/Steps/3669701)). Its year of user research concluded that people want to remember "how an activity felt, along with the people, moments, and story, more than distance or data" ([Relive new app](https://support.relive.com/kb/guide/en/your-new-relive-is-here-SkECJOTybj/Steps/4393615)). At launch, Strava Flyover took about 60 s per hour of activity, so an 8-hour hike played for about 3 minutes, with no photos and a static camera. DC Rainmaker's verdict was that it "isn't ready yet" ([DC Rainmaker](https://dcrainmaker.com/2023/11/launches-activity-flyover.html)). Pikmin Bloom's Daily Lookback is the closest structural template. A step count climbs along a zig-zag path with milestone turns, the character celebrates, the Pikmin offer one photo from the day, and the player taps a happy, neutral or sad face. "The lookback itself has no written text"; text lives in the Lifelog, capped at 300 characters ([Pikipedia: Lifelog](https://pikminwiki.com/Lifelog)). Apple's HIG asks for a summary at the end of every session and says to "discard extremely brief workout sessions" or ask whether to keep them ([Apple HIG Workouts](https://developer.apple.com/design/human-interface-guidelines/workouts.md)). Apple Journal attaches a prompt to each suggestion ("What was the highlight of your trip?") ([9to5Mac](https://9to5mac.com/2023/12/11/ios-17-2-includes-all-new-journal-app-heres-how-it-works/)). That is a precedent for seeding the one-line epilogue with a question rather than a blank field.

For the animation itself, the cheapest MapLibre route reveal is **`line-gradient` over `line-progress` on a GeoJSON source with `lineMetrics: true`**. Each frame changes one paint property, and the geometry is never re-tiled ([MapLibre line-gradient](https://maplibre.org/maplibre-gl-js/docs/examples/line-gradient/); [maplibre-react-native LineLayer](https://github.com/maplibre/maplibre-react-native/blob/HEAD/docs/LineLayer.md)). Mapbox's cinematic-route post drives everything from `phase = elapsed / duration` and places the camera target with `turf.along`. It notes that "without smoothing, the camera stays locked on the leading edge, which causes jitter at sharp turns," and fixes this with a lerp ([Mapbox blog](https://mapbox.com/blog/building-cinematic-route-animations-with-mapboxgl)). The alternative, calling `setData` every frame, hits MapLibre's repaint cost: one source took about 1 ms of a 16 ms frame just in `coveringTiles` ([maplibre-gl-js #96](https://github.com/maplibre/maplibre-gl-js/issues/96)). Moving a marker and the camera independently each frame makes the marker visibly shake ([maplibre-gl-js #4455](https://github.com/maplibre/maplibre-gl-js/issues/4455)).

For placing captures, geotagging tools agree on the recipe: take the capture timestamp and interpolate linearly between the two bracketing track fixes ([ExifTool](https://exiftool.org/geotag.html)). At a 10 s fix interval and walking pace, interpolation error is at most about 14 m. A 60 s clock skew misplaces a photo by about 83 m ([HoudahGeo](https://geotag.photos.houdah.com/geotag-photos-gpx.html)). On storage, Apple's rules are that `Documents` and `Application Support` are backed up and never purged, while `Caches` is purged under storage pressure. Apple also states that the exclude-from-backup flag "has no effect on whether iOS deletes files" ([Apple Tech Talk 204](https://developer.apple.com/videos/play/fall2017/204); [Apple Forums 107071](https://developer.apple.com/forums/thread/107071)). Expo exposes only `Paths.document` as "safe from being deleted by the system" ([Expo FileSystem](https://docs.expo.dev/versions/v58.0.0/sdk/filesystem.md)). Day One's split is a good model for export. Its automatic backups are text only, and its only media-complete format is a manual JSON zip with `photos/`, `videos/` and `audios/` folders ([Day One backups](https://dayoneapp.com/guides/backups-in-day-one-android/)). Polarsteps shows why photo locations should stay on the device. In 2026 its API exposed GPS data taken from users' photos at meter-level precision ([ITdaily](https://itdaily.com/blogs/beveiliging/polarsteps-leak-exact-location/); [Polarsteps statement](https://www.polarsteps.com/comment-follow-the-money)).

### Recommended parameters

Use a fixed duration of about 40 s for any walk length, and scale the playback speed to fit. Do not use a fixed compression ratio. Precompute every frame value on stop: progress, camera center (lerp-smoothed), bearing, and fog-layer opacity. Feed them from a single timer, capped at 30 fps on older devices with `preferredFramesPerSecond`. Drive the walker dot as a symbol layer from the same progress value as the line, not as a view annotation. Build pauses into a piecewise time map. Cluster captures that fall within a few seconds or tens of meters of each other into one stop. Give each stop about 2 s (Relive's default), and cap total pause time at roughly a third of the timeline, shortening each pause as the number of captures grows. Resample the trace by distance, so the dot moves at a steady screen speed and long dwells collapse. Stamp each capture with the app clock plus the latest accepted fix and its accuracy, then refine the position by interpolation. Walks below a minimum length get a stats card without the ceremony, per the HIG and Pikmin's 300-step "shiny" threshold ([Niantic Help](https://niantic.helpshift.com/hc/zh/23-pikmin-bloom/faq/2859-daily-lookback/)).

### What changes in the design

Little changes here, but two choices are now fixed. Originals go in a persistent directory: `Paths.document` with `enableFileSharing` off until the user exports, or `Application Support` through a small native helper. Thumbnails and rendered ceremony assets go in `Caches`. Exports become user-visible bundles: GeoJSON/GPX plus a media folder, with GPS EXIF stripped unless the user opts in. Saving to Photos should request write-only access ([Expo MediaLibrary](https://docs.expo.dev/versions/v58.0.0/sdk/media-library.md)). The design brief already favors honesty. Show every capture in chronological order rather than a curated "best of," and offer a "hide from lookbacks" toggle at the naming step. Automatic resurfacing has well-documented harms: it can "jab you in the ribs with a painful memory" ([TechRadar](https://www.techradar.com/news/google-photos-will-soon-let-you-erase-painful-memories)), and Apple's controls are "reactionary" ([512 Pixels](https://512pixels.net/2022/01/on-apples-photos-memory-feature/)). Check `Paths.availableDiskSpace` before saving each capture.

## Discovery and proximity: run checks inside the recording task, not on geofences

### How comparable apps do it

Location games avoid revealing a target precisely from a distance. Pokémon Go's Nearby list pins a Pokémon to the PokéStop it is near, and Sightings lists Pokémon only within 200 m with no distance cue ([Niantic Help](https://niantic.helpshift.com/hc/faq/2345-how-do-i-find-specific-pokemon); [Trusted Reviews](https://www.trustedreviews.com/news/pokemon-go-what-is-sightings-system-explained-guide-2946743)). Interaction radii cluster around the planned reveal distance: **Ingress uses 40 m, Pikmin Bloom's Big Flowers 40 m, and Pokémon Go 80 m.** Niantic cut Pokémon Go back to 40 m and then had to restore 80 m after community backlash that cited accessibility ([Ingress support](https://support.ingress.com/hc/en-us/articles/41140372539035-Understanding-the-Scanner); [Pikmin Wiki](https://www.PikminWiki.com/Big_flowers); [PocketGamer.biz](https://pocketgamer.biz/news/77117/niantic-restores-80-metre-interaction-radius-in-pokemon-go/)). Ingress's Nearby Portal Indicators show "the direction and distance to up to three nearby portals," a direct precedent for the ambient alert's category + distance + direction format ([Fevgames](https://fevgames.net/ingress/ingress-guide/ops/settings/)). Assassin's Creed Odyssey's "?" markers resolve only when the player arrives, and Skyrim players install mods that make undiscovered markers more generic ([GamesHedge](https://www.gameshedge.com/assassins-creed-odyssey-locations-guide-exploring-completion/); [Nexus mod](https://www.nexusmods.com/skyrimspecialedition/mods/9762)). Anonymity until arrival is something players actively want.

The anti-spam rules that are documented are blunt. Pokémon Go allows one Pokédex alert target at a time, and its nearby push covers only uncaught Pokémon, because alerting on every spawn "would ping users constantly" ([iMore](https://www.imore.com/pokemon-go-adventure-sync-nearby-feature-now-live)). Pikmin Bloom stops planting above roughly 16–20 km/h and lets players set up to 5 privacy zones of 50–300 m ([Pikmin Wiki](https://www.pikminwiki.com/Flower_planting)). The complaints are about phones that "vibrated like five times in a row" and alerts with nothing there ([Distractify](https://www.distractify.com/p/why-is-my-phone-always-buzzing-pokemon-go); [PhoneArena](https://www.phonearena.com/news/Update-to-fix-vibration-notification-bug-in-Pokemon-Gos-Nearby-feature-is-on-the-way_id88876)). **No shipped product publishes a per-session cap; the planned 2–3 per session is stricter than anything found.** On wildcards, the recommender literature shows that relevance-only personalization narrows taste: a Spotify field experiment with about 853k users found +28.9% streams but −11.5% individual diversity ([Holtz et al.](https://arxiv.org/pdf/2003.08203.pdf)). Explicit controls with immediate effect raise satisfaction ([GroupLens](https://grouplens.org/blog/putting-users-in-control-of-their-recommendations/)). Purely random picks were surprising-and-useful about half as often as relevance-constrained serendipity, 6.5% versus 12.5% ([JCST review](https://jcst.ict.ac.cn/fileup/1000-9000/PDF/2021-2-13-0135.pdf)). No study gives an optimal wildcard share.

The iOS mechanics settle the architecture. Region monitoring caps an app at 20 conditions. Events need a boundary crossing plus a "system-defined cushion," and the guide says to "assume that the minimum distance is approximately 200 meters" for testing, with at least 20 s inside ([Apple LocationAwarenessPG](https://developer.apple.com/Library/ios/documentation/UserExperience/Conceptual/LocationAwarenessPG/RegionMonitoring/RegionMonitoring.html)). Delivery takes "3 to 5 minutes on average" ([Apple startMonitoring](https://developer.apple.com/tutorials/data/documentation/corelocation/cllocationmanager/startmonitoring(for:).md)). Practitioners report that reliability drops below about 100 m ([Adobe Places FAQ](https://experienceleague.adobe.com/en/docs/places/using/places-faqs)). Expo cannot schedule `LocationNotificationTrigger` from JavaScript in any case ([Expo Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/)). Scheduling a local notification from a running background app is the supported path ([Apple: scheduling locally](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app.md)). The 64-pending-request cap does not apply to immediate notifications ([Apple Forums 811171](https://developer.apple.com/forums/thread/811171)). For direction, Apple says compass heading is the better cue at walking speed ([Apple: heading and course](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/GettingHeadings/GettingHeadings.html)). But a phone in a pocket reports pocket orientation, and course is invalid whenever `courseAccuracy < 0` ([Apple courseAccuracy](https://developer.apple.com/documentation/corelocation/cllocation/courseaccuracy.md)).

### Recommended parameters

Run every ambient, reveal and recall check as a haversine distance test inside the background location callback, against a small in-memory candidate set. Persist the session's alert state in SQLite, because the task runs headless. Fire `scheduleNotificationAsync({ trigger: null })` with `interruptionLevel: 'active'` and a per-session `threadIdentifier`. Reveal at 60–75 m rather than 50 m, and only when the current fix's accuracy is under about 30 m. With a downtown median error of 13.6 m and a 90th percentile of 48 m, 50 m will sometimes fail to fire, or fire from across a block. Pair the reveal radius with a larger "existence" radius of a few hundred meters for scan markers, following Pokémon Go's 200 m pattern. For ambient alerts, enforce the 2–3 cap, a minimum gap of about 10 minutes or 500 m, never re-alert a place that was already revealed or dismissed, suppress alerts above about 10–15 km/h, honor user quiet zones around home and work, and allow at most one vibration per alert. These rules are assembled from the precedents above, not taken from a single source. Compute direction from the bearing between the current fix and a fix 20–30 m back, accepted only when the displacement is more than 2× the accuracy. Express it in words ("ahead," "on your right"), fall back to cardinal directions, and round distances into bands. For scans, use 1–2 wildcards out of 6, still filtered for quality, and have "less" down-weight a category rather than exclude it.

### What changes in the design

**Discovery and "remind me here" have to live inside the same native-backed location session as recording.** Outside an active walk the app is not running, and geofences cannot deliver 50–75 m precision. "Remind me here" can therefore only fire during a walk, or through a coarse wake-up region of at least 100–200 m that relaunches the app (with Always authorization) so it can start precise checks. It cannot be a stand-alone 50 m geofence. Time Sensitive interruption requires a capability in the provisioning profile ([Apple Forums 683630](https://developer.apple.com/forums/thread/683630)). Default to 'active' and do not assume a free-Apple-ID sideload can carry Time Sensitive. Because Protomaps POIs lack stable ids, store revealed and dismissed places under derived keys. Expect occasional re-alerts when OSM edits move or rename a POI.

## Open gaps that need on-device answers

The biggest unknown is distribution, not geometry. None of the research verified what an unsigned IPA signed on-device with a free Apple ID can carry: the `location` background mode, Always authorization flows, the Time Sensitive capability, App Group or widget extensions for a Live Activity, or the profile's lifetime. Every recording and discovery recommendation above assumes these work. A one-day spike to check them should come before any feature work. The second unknown is termination. Apple has not confirmed whether `liveUpdates` plus a session relaunches after a user swipe-kill on iOS 26/27, or whether When In Use authorization is enough for relaunch. Reports conflict, and the iOS 26.4 regression report has no answer. The third is performance. There are no measurements of `@mapbox/vector-tile` decoding, flatbush matching or `pmtiles` range reads under Hermes on an iPhone, no documentation of React Native `fetch` honoring `Range` headers with `arrayBuffer()`, and no confirmation that expo-sqlite includes R*Tree. All of these are extrapolated from desktop Node figures. Matching thresholds have no ground truth either. No app publishes false-positive rates, so the 50–70% coverage cut and the junction discount must be calibrated on the developer's own labelled walks. A pedestrian-calibrated HMM β does not exist in the literature. Finally, MapLibre has three unresolved defects that directly affect this stack: PMTiles offline packs (#2352), the `PMTilesFileSource` request leak, and the ETag staleness bug (#4564), which was closed pending reproduction. Any of them could change, for better or worse, in a minor release.

## Conclusion

The plan's core bets hold up: the raw trace as source of truth, on-device derivation, and no backend. The incumbents' failures all trace back to the opposite choices. CityStrides' lost completions come from incremental server state. Polarsteps' privacy incident came from server-held photo metadata. Flyover's tedium came from proportional replay time. What the evidence adds is that the app's reliability lives in three thin native seams, not in its JavaScript: a `liveUpdates` recorder that rebuilds itself at launch, a tile reader that bypasses MapLibre's offline-pack assumptions, and a background callback cheap enough that iOS keeps feeding it. Discovery, recall, fog clearing and the replay ceremony all hang off that one live session. That makes the recorder the product's single point of failure, and it should be built and soak-tested on the actual sideloaded build before anything else.

The second shift concerns what "street" means. Phone GPS cannot resolve sidewalks, OSM cannot agree on how to draw them, and vector tiles drop the topology that matchers need. The honest unit is therefore a street corridor credited by covered length within a tolerance of about 20 m. That is coarser than the fog's visuals suggest, but it is stable across data refreshes and explainable to users. The incumbents ship the same idea once you look past their marketing.
